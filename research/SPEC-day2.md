## 1. 요구사항 최종 해석

### 1-1. 세 해석의 합치점 (그대로 채택)

1. **발화는 3개 기능 요청이다**: (A) 챔피언별 꿀잼 조합·아이템·스킬 증강 카탈로그, (B) 카드별 "이 증강으로 뭘 할 수 있나" 설명, (C) 리롤 확률 정보. 이 중 **(B)는 이미 구현돼 있다** (`recommend.js previewAugment` → 픽 미리보기 스트립: 루트·신규 콤보·예시템·funDelta). 재구현 금지 — (A)·(C)와 연결만 한다.
2. **"이미 나온 것/안 나온 것을 포함해서 계산" = used 집합 조건화**. `game.pool`(챔피언 조건부 풀) − `game.used`(노출·선택 전부) 위에서 `weightFor` 가중 정규화하면 **현재 라운드의 슬롯 리롤·황금 리롤 확률은 닫힌 형태로 정확하다** (리롤은 단 1회 가중 추출 — draft.js `rerollSlot`→`drawAugment`). 균등 확률로 구현하면 사용자가 정확히 간파한 부분을 배신하는 것.
3. **확률 조회는 rng를 절대 소비하지 않는다** (시드 결정론 파괴 금지). 표시 로직과 실제 추출 로직은 **단일 후보 산출기를 공유**해야 하며 (드리프트 방지), 몬테카를로 실측 빈도와 해석적 분포의 일치를 테스트로 강제한다.
4. **미래 라운드 확률("지금 스킵하면 다음에 또 보나")은 v1 제외** — 등급 롤 추정치가 복리로 겹치는 추정치라서. 단, 핵심 사실은 확률이 아니라 규칙이다: **노출된 카드는 영원히 재등장 금지**(used) — 이건 v1에서 배지로 명시한다.
5. **정직성 이중 프레임**: "이 시뮬레이터 안에서는 정확" / "실제 게임에 대해서는 모델 추정" (weightFor 2.0/0.6/1.5, tierWeights 전부 근사 상수). 정수 % 표기, 소수점 가짜 정밀도 금지, "시뮬 기준" 캡션 1회.
6. **스킬 증강 강조는 양쪽 모두에 걸린다**: 사전에는 "이 챔피언이 받는 스킬 증강 + 어느 스킬이 강화되는가" 표 (실측 306건 + spellPin 86쌍), 확률에는 (증강, 스킬) 쌍 단위 `skillOdds` (pin/slot=확정, 그 외 적격 스킬 균등 — 균등 자체가 ③ 근사임을 주석).
7. **다음 리롤 결과의 스포일러 금지** — 시드 결정론상 다음 카드를 미리 볼 수 있지만, 분포만 보여주고 결과는 감춘다 (리롤 도박의 재미 보존).

## 2. 기능 A — 챔피언 꿀잼 사전

### 2-1. 화면 구조 (SPA 4번째 화면, 해시 `#dex/{챔피언id}`)

- **진입점 3곳**: ① 챔피언 선택 화면 미리보기 패널의 "꿀잼 사전 보기" 버튼 ② 드래프트 화면 헤더의 챔피언 초상 탭 ③ 결과 화면의 챔피언 이름 링크. 뒤로가기는 해시 히스토리(이미 SPA 해시 라우팅이면 관례 따름, 아니면 명시적 "닫기").
- **섹션 순서** (모바일 세로 1열):
  1. 헤더: 초상·이름·클래스 태그·꿀잼 티어(funrank)·한 줄 컨셉 (기존 미리보기 패널 재사용)
  2. **꿀잼 조합 카드 목록**: `synergies.json` combos 중 이 챔피언에 적용 가능한 것 전부 — 제목·whyFun·구성 증강(등급 테두리)·핵심 아이템. 정렬은 funScore/시그니처 우선.
  3. **스킬 증강 표** (스킬 증강 강조 요구의 본체): 이 챔피언의 `eligibleAugments` 중 `category==='ability'` 전부를 행으로. 각 행: 증강명·등급·**강화 대상 스킬** — spellPin/slot이면 "Q가 강화됨(확정)" + 스킬 한국어명, 아니면 적격 스킬 목록("Q/W/E 중 무작위 지정 — 근사"). `research/data/ability-augment-map.json` 실측 306건이 근거인 행은 "실측" 배지. spellExclude로 제외된 스킬은 취소선+사유.
  4. **예시 아이템**: recommend.js fitScore 상위 아이템 6~8개 (조합 카드에 이미 박힌 것과 중복 허용 — 여긴 "범용 추천").
  5. 캡션: "시뮬레이터 기준 — 실제 풀·가중치는 서버 전용" 1회.

### 2-2. 데이터·계산

- 신규 데이터 파일 없음. 전부 기존 로드분(`augments/champions/synergies/funrank` + eligibleAugments)에서 파생. 사전 화면 렌더 시 `eligibleAugments(augments, champion)` 1회 호출로 풀 확정 → category 분류.
- 스킬 증강 표의 "확정" 판정은 draft.js `presentAugment` 우선순위 ①spellPin ②slot과 **동일 로직**이어야 한다 — recommend.js 또는 공용 헬퍼로 추출해 사전과 드래프트가 같은 답을 내게 한다 (드리프트 방지 원칙과 동일).

### 2-3. 콤보 0건 폴백 (필수)

combos는 70건 — 173명 중 상당수가 0건이다. 콤보 섹션이 비면: tagRules 기반 일반 루트 2~3개(recommend.js recommend의 태그 점수화 재사용) + 스킬 증강 표(306건 실측이 커버) + 예시템으로 채워 "챔프를 누르면 나온다"는 기대를 배신하지 않는다. "이 챔피언은 전용 콤보가 아직 없어요 — 범용 루트 추천" 문구 명시.

### 2-4. 제약 준수

- 모든 텍스트는 textContent (XSS 규율). 상대 경로만. 의존성 0. 화면 추가로 index.html에 섹션 1개 + app.css 스타일 — 기존 화면 전환 패턴(챔피언 선택→드래프트→결과) 관례를 따른다.

## 3. 기능 B — 리롤 확률 어드바이저

### 3-1. 확률 정식 (math 해석 채택, draft.js 실코드와 대조 완료)

챔피언 c, 조건부 풀 P_c = eligibleAugments(A, c) = `game.pool`, 사용 집합 U = `game.used` (apiName). 슬롯 i의 카드 등급 τ = `round.slots[i].tier` (라운드 등급이 아니라 **카드 자신의 tier** — 폴백·황금 리롤로 다를 수 있음. 근거: `rerollSlot`이 `current.tier`로 뽑음).

**후보 집합 (폴백 해소 포함)** — `drawAugment`의 시도 순서를 그대로 미러:

```
order = [τ] ++ FALLBACK_ORDER[τ]            (일반 리롤)
order = [TIER_UP[τ]] ++ FALLBACK_ORDER_UPGRADE[τ]   (황금 리롤)
τ* = order에서 처음으로 C_t ≠ ∅ 인 등급,  C_t = { a ∈ P_c \ U : tier(a) = t }
C = C_{τ*}
```

**단일 증강 적중 확률** (가중 추출):

```
Pr[a] = w(a) / Σ_{b∈C} w(b),   w(a) = weightFor(a, c, {trackL9})
(방어: Σw ≤ 0 이면 균등 1/|C| — drawAugment의 균등 폴백 미러)
```

**목표 집합 T 적중 확률** (예: "혈검 온힛 루트를 여는 증강들"):

```
Pr[리롤이 T 적중] = Σ_{a ∈ T∩C} w(a) / Σ_{b∈C} w(b)
```

**(증강, 스킬) 쌍 확률** — `presentAugment` 우선순위 ①②③ 미러:

```
Pr[(a,k)] = Pr[a] · q_a(k)
q_a(k) = 1[k = pin/slot]              (①② 결정적 — pin·exclude 충돌 시 ③으로 강등되는 예외까지 미러)
       = 1/|S_a|  (k ∈ S_a)           (③ 적격 스킬 균등 — 근사)
       = 0        (그 외)
```

**계산 가능성 경계** (UI 문구·주석의 근거):

| 대상 | 지위 |
|---|---|
| 현재 라운드 슬롯 리롤 / 황금 리롤 | 시뮬레이터 내 **정확** (닫힌 형태, 단일 추출) |
| 미래 라운드 등장 확률 | 추정만 가능 (등급 롤 근사 × 경로 의존 U × 3장 순차 비복원) → **v1 제외** |
| 실제 게임 확률 | 원리적 불가 (가중치·게이트 전부 서버 전용) → "시뮬 기준" 고지 |

`previewAugment`가 카드마다 산출하는 루트(매칭 combo들)의 구성 증강 중 **아직 안 나온 것**(P_c \ U ∩ 콤보 참조 증강)을 T로 반환하는 헬퍼 `routeTargets(previewInfo, game)` 신설 → apiName Set. 스킬 증강이 목표일 때는 (aug, skill) 쌍 지원: `hitProbability` 결과에 `skillOdds`를 곱해 앱 계층에서 합성.

### 3-4. 카드 UI 배치 (모바일 우선)

1. **라운드 스트립 1개** (등급 배지 바로 아래, 카드 밖): "리롤하면 — S급 12% · 스킬증강 22% · 남은 골드 31개". 분모·분자 함께 노출이 원칙("골드 31개 중 루트 3개")  — 사용자의 멘탈 모델("나온 것/안 나온 것")을 그대로 확인시킴. 황금 리롤 미사용 시 "황금 리롤 시: …" 줄 추가. 리롤/황금 리롤 후 전체 재렌더로 자동 갱신.
2. **카드별 1줄** (기존 픽 미리보기 스트립에 이어붙임): "→ 이 루트 증강이 리롤에서 또 나올 확률 9% (잔여 3개)". 현재 카드가 이미 T에 속하면: "**지금 먹으면 확정 — 리롤은 이 카드를 영구 소각하고 9%에 거는 것**" (비대칭 경고, math F-D).
3. **재등장 금지 배지**: 카드에 한 번 노출된 증강은 다시 안 나온다는 규칙을 스트립 캡션 또는 첫 라운드 1회 안내로 명시 ("지금 화면의 카드는 이번 판에 다시 안 나와요").
4. 표기 규율: 정수 % (1% 미만은 "<1%"), "시뮬 기준" 캡션 1회(라운드 스트립 끝). 소진 시(`round.rerolled[i]`·`goldenUsed`) 해당 줄 비활성/제거. 카드 탭=픽 인터랙션은 **불변** (ux 위험 7 — 탭 대상 추가 금지, 상세 시트는 이번에 안 만든다).

### 3-5. "먹을까/리롤할까" 추천 규칙 (3밴드, 유보 톤)

숫자 위임이 원칙(B1)이되, 다음 밴드 힌트를 카드 1줄 끝에 조건부로 붙인다 (§6 사용자 확인 후 활성화):

```
E[리롤 funScore] = Σ p(a)·funScore(a)   (rerollDistribution 위에서)
d = E[리롤] − funScore(현재 카드)
d > +8  → "리롤 각 ▲"      d < −8 → "먹는 각 ▼"      그 외 → "반반 ―"
단, 현재 카드 ∈ T(진행 중 루트)면 밴드와 무관하게 "먹는 각(루트 확정)" 우선.
임계 ±8은 funScore 0~100 스케일의 근사 상수 — "근사:" 주석 필수.
```

단정 어미 금지("~각" 유지) — 근사 가중치 위의 판단임을 톤으로 전달.

### 3-6. 정직성 고지 (무엇이 정확하고 무엇이 추정인가)

- **정확 (시뮬레이터 내)**: 현재 라운드 슬롯 리롤·황금 리롤의 증강별/집합 확률, 잔여 풀 수, resolvedTier 폴백, 재등장 금지 규칙.
- **추정 (근사 상수 위의 값)**: weightFor 계수(2.0/0.6/1.5)·trackL9(1.5)·tierWeights — 즉 표시되는 모든 %는 "시뮬레이터 모델 기준". ③ 무작위 스킬 지정의 균등 가정. UI 캡션 1회 + 코드 "근사:" 주석(검증 에이전트 감사 대상).
- **표시하지 않는 것**: 다음 리롤의 실제 결과(스포일러 금지), 미래 라운드 확률(v1 제외), 실게임 확률 단정.

## 5. 검증 계획

1. **결정론 회귀 (최우선)**: drawAugment 리팩터 후 기존 테스트 5종(test-draft/recommend/e2e/validate-data/montecarlo) 무수정 통과 = 시드별 드래프트 결과 바이트 동일의 증명. 추가로 리팩터 전후 동일 시드 100게임의 전체 이력 스냅샷 diff 테스트를 test-odds에 포함.
2. **분포 불변식 단위 테스트**: Σp = 1 (±1e-9), entries ⊆ pool−used, entries의 weight가 weightFor 재호출값과 일치, entries 순서 = pool 순서, resolvedTier가 폴백 순서 규칙과 일치(고갈 강제 시나리오 — 풀을 인위 축소해 FALLBACK_ORDER / FALLBACK_ORDER_UPGRADE 각 분기 커버), 전 고갈 시 entries=[].
3. **몬테카를로 대조 (핵심)**: 시나리오별(챔피언 3종 이상 × 라운드 등급 × trackL9 on/off × 황금 리롤) 상태를 고정하고 서로 다른 시드 N=100,000회로 `rerollSlot`/`goldenReroll`을 1회씩 실행(상태는 JSON 복제로 매회 복원) → 실측 빈도 vs `rerollDistribution`/`goldenDistribution`의 p를 증강 단위로 대조. 판정: 각 증강의 |실측−p| < 4·√(p(1−p)/N) (4σ) 전 항목 통과. `skillOdds`도 동일 방식으로 `presentAugment` 실측과 대조(①확정=빈도 1.0, ③균등 검증).
4. **hitProbability 대조**: 목표 집합 T를 랜덤 구성해 Σ(개별 p) = hitProbability 일치 + 몬테카를로 집합 적중 빈도 대조.
5. **UI/E2E**: test-e2e에 사전 화면 렌더(콤보 있음/0건 폴백 각 1명), 라운드 스트립 %가 rerollDistribution과 일치, 소진 시 비활성, XSS 규율(textContent) 확인 추가.
6. **감사 규율**: 신규 근사(임계 ±8, ③ 균등 가정)에 "근사:" 주석 — validate-data 또는 검증 에이전트 감사 통과.

## 6. 사용자 확인 필요 사항

1. **단정형 추천 힌트**: "먹는 각/반반/리롤 각" 3밴드 힌트까지 표시할까요, 아니면 확률 숫자만 둘까요? (원문은 "확률을 알 수 있게 해줘"라서 v1 기본은 숫자만 + 루트 확정 경고이고, 밴드 힌트는 규칙만 준비해 둔 상태로 확인 후 켭니다.)
2. **챔피언 사전을 별도 화면으로**: "챔프를 누르면"을 전용 사전 화면(#dex, 조합+아이템+스킬증강 표 전체)으로 구현합니다. 기존 미리보기 패널의 인라인 확장 정도면 충분했다면 알려주세요 — 화면 추가는 구조 변경이라 확인받고 진행하는 게 안전합니다.
3. **미래 라운드 확률은 v2로 미룸**: "지금 안 먹으면 다음 라운드에 또 볼 확률"은 추정치(등급 롤 근사가 복리)라 v1에서 뺐고, 대신 "노출된 카드는 이번 판에 다시 안 나온다"는 규칙만 명시합니다. 이 추정치도 원하시면 v2로 추가합니다.
